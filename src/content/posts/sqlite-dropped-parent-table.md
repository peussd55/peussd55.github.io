> - **문제** — 사내 운영 포털의 DB 마이그레이션에서 안 쓰게 된 테이블을 지우려 했어요. 그 테이블을 가리키는 컬럼을 다 비우고 지우면 외래키 검사와 무결성 검사는 통과하는데, 신청을 넣는 `INSERT`와 지우는 `DELETE`가 `no such table`로 실패했어요.
> - **원인** — 검사는 행의 값을 보는데 값은 다 NULL이라 볼 것이 없었어요. 쓰기는 달라요. SQLite는 외래키가 걸린 테이블에 쓰는 문장을 준비할 때 부모 테이블을 찾아요.
> - **한 일** — 테이블은 지우지 않고 행만 지웠어요. 마이그레이션 테스트에는 검사에 더해 실제로 넣고 지워 보는 확인도 더했어요.
> - **확인한 것과 못 한 것** — 운영에서 난 장애가 아니에요. 마이그레이션을 쓰기 전에 재현으로 잡았고, 운영 DB 사본 리허설을 거쳐 배포했어요. 배포 뒤 운영에서 새 신청이 들어간 기록은 확인하지 못했어요.

## 지우려던 테이블

사내 운영 포털 이야기예요. 직원이 외부 AI 모델의 사용 한도나 모델 추가를 신청하면 처리해 주는 도구이고, DB는 SQLite 파일 하나예요. 10월 버전에는 LLM 챗봇인 도우미가 있었는데, 11월에 도우미를 걷어 내고 화면을 대시보드로 개편했어요. 그 경위는 [이 포털에서 '끝'의 기준을 다시 적은 글](/posts/done-before-anyone-looked/)에 있어요.

도우미 코드는 먼저 걷어 냈고, 도우미가 쓰던 테이블은 DB 버전을 하나 올리는 마이그레이션에서 한꺼번에 지우기로 했어요. 그 가운데 도우미 대화 테이블은 신청 테이블의 컬럼 하나가 외래키로 가리키고 있었어요.

명세에는 순서가 적혀 있었어요. 지우기 전에 가리키는 컬럼부터 NULL로 비운다는 내용이었어요. 10월에 이전 버전 마이그레이션을 운영 DB 사본으로 리허설하다가 배운 것이었어요. 그때는 사본에서 대화를 지우자 신청 두 건의 참조가 끊겨 외래키에서 실패했어요.

리허설 계획도 같은 가정을 깔고 있었어요. 운영 DB 사본에 마이그레이션을 돌린 뒤 외래키 위반이 0인지 보고 행 수를 대조하는 계획이었어요.

## 서브에이전트가 쓰기 전에 멈췄어요

11월 초, 코딩 에이전트(이하 에이전트)가 이 마이그레이션을 서브에이전트에게 맡겼어요. 쓰기 전에 스키마 제약부터 확인하고, 테이블을 다시 만들어야 하는 곳이 나오면 멈춰서 보고하라는 조건을 붙였어요. 서브에이전트는 십 분이 안 돼 멈췄어요. 보고한 두 곳 가운데 하나는 대화 테이블을 지우면 신청 테이블의 쓰기가 막힌다는 내용이었어요.

에이전트는 이 주장부터 작은 스크립트로 직접 확인했어요. 같은 모양을 다시 쓰면 아래와 같아요.

이 글의 코드는 실제 업무 코드가 아니에요. 문제를 재현하려고 같은 모양으로 새로 쓴 코드이고, Node.js 24에 든 `node:sqlite`로 그대로 돌아가요.

```js
import { DatabaseSync }
  from 'node:sqlite';

const db =
  new DatabaseSync(':memory:');
// 운영 연결처럼 외래키 검사를 켜요
db.exec('PRAGMA foreign_keys = ON');
db.exec(`
  CREATE TABLE chats (
    id INTEGER PRIMARY KEY
  );
  CREATE TABLE requests (
    id INTEGER PRIMARY KEY,
    title TEXT,
    chat_id INTEGER
      REFERENCES chats(id)
      ON DELETE SET NULL
  );
  INSERT INTO chats VALUES (1);
  INSERT INTO requests
    VALUES (1, 'first', 1);
`);

// 명세대로: 참조를 비우고 부모를 지워요
db.exec(`
  UPDATE requests SET chat_id = NULL;
  DROP TABLE chats;
`);
```

가리키는 행이 없으니 `DROP TABLE`은 오류 없이 끝나요. 이어서 검사 둘과 쓰기 셋을 해 봐요.

```js
const rows = (sql) => JSON.stringify(
  db.prepare(sql).all(),
);
const write = (sql) => {
  try {
    db.exec(sql);
    return 'ok';
  } catch (e) {
    return e.message;
  }
};

console.log([
  rows('PRAGMA foreign_key_check'),
  rows('PRAGMA quick_check'),
  write(`INSERT INTO requests (title)
         VALUES ('second')`),
  write('DELETE FROM requests'),
  write(`UPDATE requests
         SET title = 'x'`),
].join('\n'));
```

```text
[]
[{"quick_check":"ok"}]
no such table: main.chats
no such table: main.chats
ok
```

외래키 검사는 위반 0건이고 무결성 검사는 ok예요. 그런데 `INSERT`와 `DELETE`는 없는 테이블을 찾다가 실패해요. 새 행의 참조 컬럼이 NULL이어도 같아요. 되는 것은 `SELECT`와, 참조 컬럼을 건드리지 않는 `UPDATE`뿐이에요. 포털로 옮기면 새 신청이 접수되지 않는 상태예요.

## 검사는 행을 보고, 쓰기는 테이블 정의를 봐요

`foreign_key_check`는 자식 테이블의 행마다 가리키는 부모 행이 있는지 봐요. 값이 NULL인 행은 위반이 아니에요. 컬럼을 다 비웠으니 볼 행이 없었어요. 값이 남아 있었다면 이 검사가 그 행을 짚어요. 10월에 걸린 것은 값이 남아 있던 쪽이에요. `quick_check`는 파일과 테이블 구조를 보는 검사라 외래키는 보지 않아요.

쓰기는 행이 아니라 테이블 정의를 봐요. 신청 테이블 정의에는 `REFERENCES chats(id)`가 그대로 남아 있어요. SQLite는 외래키 검사가 켜진 연결에서 이런 테이블에 쓰는 문장을 준비할 때 부모 테이블을 찾고, 없으면 그 자리에서 오류를 내요. SQLite 문서에도 부모 테이블이 없으면 `no such table`이 난다고 적혀 있어요.

틀린 가정은 둘이었어요. 가리키는 행이 없으면 부모 테이블을 지워도 된다는 것, 그리고 검사가 통과하면 쓰기도 된다는 것이에요. 10월에 배운 것은 반만 맞았어요.

하나 더 있어요. 외래키 검사를 끈 연결에서는 위의 `INSERT`와 `DELETE`가 그대로 돼요. SQLite의 외래키 검사는 연결마다 켜야 하고 기본값은 꺼짐이에요(`node:sqlite`는 켠 채로 열어요). 사본을 어떤 도구로 열어 보느냐에 따라 이 문제는 보이지 않을 수 있어요. 포털의 운영 연결은 켜져 있었어요.

## 테이블은 남기고 행만 지웠어요

길은 둘이었어요. 하나는 신청 테이블을 외래키 없이 다시 만드는 것이에요. 포털에서 가장 많이 쓰는 테이블을 새로 만들어 옮기는 일이라, 에이전트는 트리거와 번호를 그대로 이어받게 하는 것을 위험으로 들었어요. 다른 하나는 대화 테이블을 지우지 않고 행만 지우는 것이에요. 대화 기록을 지운다는 원래 목적은 그대로 이뤄요. 대신 아무 코드도 쓰지 않는 빈 테이블이 남아요.

에이전트는 뒤쪽을 권했고 저는 그쪽을 골랐어요. 도우미가 쓰던 나머지 테이블은 계획대로 지웠어요.

```js
// 고친 마이그레이션: 행만 지워요
db.exec(`
  UPDATE requests SET chat_id = NULL;
  DELETE FROM chats;
`);

// 검사에 더해 실제로 써 봐요
const probe = `
  INSERT INTO requests (title)
  VALUES ('probe');
  DELETE FROM requests
  WHERE title = 'probe';
`;
db.exec(probe);

// 지우면 막힌다는 것도 고정해요
db.exec('BEGIN');
db.exec('DROP TABLE chats');
assert.throws(
  () => db.exec(probe),
  /no such table: main\.chats/,
);
db.exec('ROLLBACK');
```

첫 코드 블록의 마지막 `db.exec`를 이 코드로 바꾸고 맨 위에 `import assert from 'node:assert';`를 더하면 오류 없이 끝나요. 마이그레이션 테스트에 넣은 것도 이 둘이에요. 마이그레이션 뒤에 신청 테이블에 실제로 넣고 지워 보는 것, 그리고 트랜잭션 안에서 대화 테이블을 지워 본 뒤 쓰기가 실패하는 것을 확인하고 되돌리는 것이에요. 뒤의 것은 테이블을 남긴 이유를 테스트로 고정해 둔 거예요.

## 확인한 것과 남은 것

문제를 찾은 것은 서브에이전트이고, 재현으로 확인한 것은 에이전트예요. 저는 리허설에 쓸 운영 DB 사본을 떠도 된다고 했고, 두 길 가운데 하나를 골랐고, 배포 스크립트를 돌렸어요.

마이그레이션을 다 쓴 뒤 에이전트가 운영 DB를 읽기 전용으로 떠서 리허설했어요. DB 버전이 하나 올랐고, 다시 돌리면 적용할 것이 없었어요. 무결성 검사 ok, 외래키 위반 0, 남는 테이블의 행 수는 전부 그대로였어요. 여기에 신청 테이블의 `INSERT` · `DELETE` · `UPDATE`를 실제로 해 보는 확인을 더했어요. 직원 데이터가 든 사본은 리허설을 마친 자리에서 지웠어요. 개편은 11월 중순에 배포했어요. 배포 직후 제가 관리자 화면에서 승인을 기다리던 신청 하나를 승인했고, 정상적으로 반영됐어요.

확인하지 못한 것은 이래요.

- 운영에서 난 장애가 아니라서, 신청이 막히는 모습을 포털 화면에서 본 적은 없어요. 확인은 재현 스크립트와 테스트에서 한 것이에요.
- 배포 뒤 운영에서 새 신청이 들어간 기록은 확인하지 못했어요. 배포 직후에 승인한 것은 배포 전에 옛 화면으로 들어와 있던 신청이에요. 이미 있는 행을 고치는 쪽이라, 새 행을 넣는 경로를 확인한 것은 아니에요.
- 빈 테이블은 지금도 남아 있어요. 없애려면 신청 테이블을 다시 만들어야 해요.

다시 한다면 바꿀 것은 두 가지예요.

- **테이블을 지우기 전에 그 테이블을 가리키는 외래키부터 찾아요.** 행이 아니라 테이블 정의에서 찾아요. 참조하는 값을 다 비워도 정의는 남아요.
- **마이그레이션 검증에 실제 쓰기를 넣어요.** 검사가 통과했다는 것과 쓸 수 있다는 것은 다른 말이었어요. 운영과 같은 연결 설정으로 넣고 지워 봐요.

이 글의 일은 코딩 에이전트와 함께 했어요. 무엇을 누가 했는지는 본문에 적었어요.

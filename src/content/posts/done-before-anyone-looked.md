> - **문제** — 코딩 에이전트가 사내 운영 포털의 2차 구현을 마감하며 "구현을 끝냈습니다"라고 보고했어요. 가짜 외부 서비스와 녹화된 모델 응답 위에서 돌아간 자동 테스트가 모두 통과했다는 것이 근거였고, 새 화면을 사람이 본 흔적은 없었어요. 다음 날 제가 운영 데이터 사본으로 직접 써 보니 로그인하고 10분 남짓 사이에 결함 셋이 나왔어요.
> - **한 일** — 진단은 둘이었어요. 에이전트는 검증이 엉뚱한 것을 쟀다고 했고, 저는 화면과 도우미를 밑바닥부터 직접 짠 데 원인이 있다고 봤어요. 그날 '끝'의 기준을 화면 캡처 · 운영 데이터 사본 · 실제 모델과의 대화 · 사람이 보는 확인 지점으로 다시 적었고(에이전트 제안), 저는 일을 태스크 단위로 나누고 검증된 기반을 쓰자는 방침을 다시 말했어요.
> - **확인한 것과 못 한 것** — 새로 적은 기준이 다 지켜지지는 않았어요. 사람이 보는 확인 지점은 뒤로 밀리거나 에이전트에게 넘어갔고, 그 방침은 11월 초에 네 번째로 다시 말해야 했어요. 한 달 뒤 화면을 프레임워크로 다시 짠 대시보드 버전도 배포 전 확인에서는 외부 서비스가 가짜였어요. 결함이 밑바닥부터 짠 탓이었는지는 잰 적이 없어요.
> - **이 글** — '끝'을 누가 무엇으로 정했는지, 무엇 위에 지었는지, 그 뒤 지켜진 곳과 어긴 곳을 적어요.

## 먼저, 이 글에 나오는 것들

이 글의 주인공은 몇십 명이 쓰는 사내 운영 포털이에요. 회사가 쓰는 외부 모델 중계 서비스(여러 AI 모델을 한 API로 쓰게 해 주는 서비스)의 사용 한도를 늘려 달라거나 모델을 추가해 달라는 직원 요청을 받아 처리해요. 1차 버전은 이미 운영 중이었어요.

- **포털 서버** — 직원 화면과 관리자 화면의 요청을 받아 DB에 적어요.
- **실행기** — 외부 서비스에 실제로 쓰는 일을 맡은 별도 프로세스예요.
- **도우미** — 10월 버전에 있던 LLM 챗봇이에요. Anthropic의 작은 모델이 도구로 데이터를 조회해 답하고, 조회한 표는 카드로 붙어요.
- **자동 테스트** — 외부 서비스 · 메일 · 푸시는 가짜 서버로, 도우미의 모델 응답은 녹화본으로 바꿔 돌려요.
- **운영 데이터 사본** — 운영 DB를 읽기 전용으로 떠 와서 제 PC에만 띄운 것이에요. 이걸로 띄운 화면을 미리 보기라고 불러요.

요청은 화면 → 포털 서버 → DB로 들어가고, 실행기가 DB를 읽어 외부 서비스에 쓴 뒤 결과를 DB에 돌려놓아요. 코딩 에이전트(이하 에이전트)가 이 전체를 만들고 테스트했어요. 저는 몇 가지 방향을 정했고, 나머지는 대부분 에이전트의 권고를 승인했어요.

이 글에는 줄기가 둘 있어요. '끝'을 무엇으로 판단했느냐와, 무엇 위에 지었느냐예요. '구현 끝'이라고 보고했을 때의 화면은 빌드 도구도 화면 프레임워크도 없이 바닐라 JS로 직접 짠 코드였고, 도우미도 직접 짰어요. 서버만 널리 쓰이는 웹 프레임워크 위에 올라가 있었어요. 한 달 뒤 대시보드 형태로 다시 개발한 버전은 화면을 프레임워크와 UI 키트로 짰어요.

| 언제 | 무슨 일 | '끝'을 판단한 것 |
|---|---|---|
| 10월, 마감한 날 | 에이전트가 2차 구현을 마감하고 "구현을 끝냈습니다"라고 보고 | 자동 테스트 |
| 다음 날 오후 | 제가 써 보고 10분 남짓에 결함 셋 · 진단 둘 · '끝'을 다시 적음 | 사람의 사용 |
| 그날 저녁 | 에이전트가 화면 283장을 찍어 결함 60건 찾음 | 캡처와 자동 점검 |
| 그 며칠 뒤 | 두 번째 미리 보기 · 점검은 에이전트에게 맡김 | 에이전트의 점검 |
| 마감 열흘쯤 뒤 | 도우미를 걷어 내고 대시보드로 개편하기로 함 | — |
| 마감 한 달 뒤 | 화면을 프레임워크로 다시 짠 대시보드 버전 · 배포 전 확인 단계 | 화면 → 포털 → 실행기 테스트 |

## "구현을 끝냈습니다"는 테스트 숫자였고, 화면은 아무도 보지 않았어요

10월 어느 날 밤, 에이전트가 마감 보고를 올렸어요. "구현을 끝냈습니다." 근거는 숫자였어요. 자동 테스트 3,208개, 서버를 띄워 끝까지 도는 테스트 26개, 브라우저 테스트 72개가 모두 통과했어요. 다음 날 오후 저는 그 새 버전을 제 PC에 띄운 미리 보기에 로그인했고, 10분 남짓 사이에 결함 셋을 짚었어요.

구현 순서는 제가 정한 대로였어요. 그때는 에이전트를 많이 띄워 일을 시키면 한 번에 결과가 잘 나올 거라고 순진하게 생각했어요. 설계 · 구현 워크플로 뒤에 마지막 워크플로에서 통합 · 배포 · 실서버 검증을 하는 순서였고, 사람이 화면을 대조하는 일은 처음부터 맨 끝 묶음에 있었어요. 구현은 며칠 전부터 진행됐고, 마감한 날 하루에만 대형 멀티에이전트 워크플로가 아홉 번 돌며 토큰 수천만 개를 썼어요.

그 테스트가 돌아간 곳은 가짜 외부 서비스와 녹화된 모델 응답의 세계였어요. 3,208개는 하위 테스트까지 센 수예요. 26개는 화면 없이 포털과 실행기를 띄우고 API로 흐름을 끝까지 도는 테스트였고, 72개는 브라우저에서 화면 요소가 존재하는지와 눌리는지를 봤어요. 다음 날 에이전트는 이 숫자들로 확인한 건 코드가 명세대로 짜였는지였고, 사람이 실제로 보는 화면과 실제 모델이 내는 답은 아무도 보지 않았다고 스스로 정리했어요.

다음 날 아침 제 첫 물음은 이랬어요.

> "지난 시간까지 구현을 다 끝낸 걸로 알고 있는데 … UI도 거의 그대로인 거 같은데"

에이전트는 새 버전이 아직 제 PC에만 있고 스타일 변경이 크지 않아 겉모습은 비슷할 거라며, 배포 전에 PC에서 띄워 보자고 권했어요. '끝'이라는 말을 한 쪽은 에이전트였어요. 그날 오후 미리 보기를 띄우기 전까지 제가 새 화면을 본 흔적은 기록에 없어요.

## 운영 데이터 사본에서 10분 남짓 사이에 결함 셋이 나왔고, 하나는 테스트가 지키라던 설정이 만든 것이었어요

그날 오후 저는 저 혼자 대화를 몇 번 쳐 보며 UI를 보고 싶다고 했어요. 에이전트는 운영 서버에 먼저 올리면 모든 직원이 반쯤 설정된 화면을 보게 되고, 새 실행기가 외부 서비스의 한도를 실제로 건드린다며 반대했어요. 채팅을 치면 데이터가 나와야 하지 않느냐는 제 물음에는 빈 DB나 가짜 데이터 대신 운영 DB 사본을 권했어요. 배포용 마이그레이션도 미리 리허설할 수 있다는 이유였어요. 저는 사본을 골랐어요.

에이전트는 운영 DB를 읽기 전용으로 떠 온 뒤 다른 직원의 대화와 로그인 정보, 보내려고 쌓여 있던 메일을 지우고 알림이 나가지 않게 막았어요. 외부 서비스에 쓰는 실행기는 띄우지 않았는데, 한 달 뒤 이 빈자리가 다시 나와요.

로그인하고 10분 남짓 사이에 저는 세 가지를 짚었어요. 둘째와 셋째의 원인은 에이전트가 그 자리에서 찾았고, 첫째의 원인은 그날 저녁 화면 점검에서 드러났어요.

| 결함 | 제가 본 것 | 테스트가 놓친 자리 |
|---|---|---|
| ① 가려진 버튼 | 채팅 카드의 [더 보기] 버튼 아래쪽이 덮임 | 높이 상한과 펼친 줄 수만 셈 · 가려지는지는 안 봄 |
| ② 없는 버튼 안내 | 카드도 없는데 카드의 버튼을 누르라는 답 | 도구를 건너뛰는 경우가 녹화본에 없음 · 글과 카드의 짝은 안 봄 |
| ③ 끊긴 답 | 저장된 답 원문부터 34자에서 끊김 | 출력 상한에 걸리는 경우가 녹화본에 없음 |

첫째 결함의 높이 상한은 며칠 전 제 불만에서 왔어요. 그때 에이전트가 브라우저로 재 보니 모델 목록 카드 하나가 4,095px까지 늘어나 있었어요. 그래서 2차 구현에서는 카드에 분류별로 몇 줄만 보여 주고 [더 보기]를 두는 한편, 본문 높이를 최대 480px로 묶어 넘치는 부분을 숨겼어요. 그날 저녁 화면 점검에서 같은 카드를 재 보니, 480px에서 자르는 설정 때문에 [더 보기] 버튼이 절반쯤 가려졌고 버튼을 눌러도 펼친 줄이 상자 밖에 생겼어요.

그날 에이전트는 브라우저 테스트가 동작만 봤고 모양은 어떤 테스트도 보지 않았다고 설명했어요. 이 글을 준비하며 기록을 다시 보니 그 설명은 반만 맞았어요. 카드 크기를 보는 브라우저 테스트는 바로 그 높이 상한을 통과 조건으로 걸어 두고 있었어요. 펼친 줄은 숨김 속성이 풀린 줄 수로 셌고, 그 줄이 상자 안에 실제로 보이는지는 보지 않았어요. 테스트는 상한을 지켰는지를 봤고, 그 상한이 버튼을 가렸어요.

그림에서는 가운데의 굵은 선을 보면 돼요. 테스트가 확인한 높이와 줄 수는 모두 통과였고, 버튼의 아래쪽과 펼친 줄은 선 아래에 있었어요.

둘째 결함은 카드가 붙는 경로에 원인이 있었어요. 카드는 모델이 도구를 불렀을 때만 붙었는데, 그날 모델은 도구를 부르지 않고 답하면서 이용 안내 문서의 '카드가 있을 때' 문장을 그대로 옮겼어요.

셋째 결함은 덮어쓰기 문제였어요. 웹 검색 질문에 모델이 쓴 1,066토큰짜리 답이 숫자 대조에서 어긋나자 서버가 다시 쓰게 했어요. 이 호출은 출력 상한 1,200토큰에 걸려 끊겼고, 끊긴 글이 원래 답을 덮어쓰고 '수리됨'으로 저장됐어요. 1,200토큰을 내고도 왜 34자만 남았는지는 그날 풀리지 않았어요.

## 진단은 둘이었어요 — 에이전트는 검증이 엉뚱한 것을 쟀다고 했고, 저는 밑바닥부터 직접 짠 데 원인이 있다고 봤어요

셋째 결함을 짚은 직후 저는 이렇게 말했어요.

> "진짜 해도 해도 너무한 거 아니냐. … 토큰을 하마처럼 퍼먹으면서 만들었는데 이게 그렇게 어려운 작업인가? 기능을 좀 명확하고 단순화할까?"

에이전트의 답은 이렇게 시작했어요. "어려운 작업이어서 이렇게 된 게 아닙니다." 원인은 둘이고 둘 다 자기 진행 방식에 있다고 했어요. 하나는 검증이 엉뚱한 것을 쟀다는 것이었어요. 테스트 숫자만 보고 '구현 끝'이라고 보고했고, 제가 몇 번 써 본 것만으로 결함이 셋 나온 게 그 증거라고 했어요. 다른 하나는 너무 크게 만들었다는 것이었어요. 도우미는 LLM이 자유롭게 말하게 둔 뒤 숫자 대조, 다시 쓰기, 가리기 같은 안전장치를 겹겹이 붙인 구조였고, 둘째와 셋째 결함이 이 이음매에서 났다고 했어요. 몇십 명이 쓰는 사내 도구인데 코드가 10만 줄 가까이 됐고, 명세는 2만 줄대였으며, DB 테이블 50여 개 가운데 3분의 1은 빈 테이블이었어요. 그날 에이전트가 처음 집계했다가, 같은 날 다시 조사해 일부를 스스로 바로잡은 수치예요.

제가 본 원인은 달랐어요. 조금 뒤 저는 이렇게 말했어요.

> "후.. 나 그냥 솔직히 몇만 줄 코드랑 명세 만드느니 프레임워크로 다시 만들고 싶은 심정이야. 어드민 기능이나, 생성형 AI 챗봇 프레임워크나 디자인도 요즘 다 템플릿 다 있는데. …"

그러고는 기획과 기능 명세부터 다시 정의하자고 했고, 에이전트도 그쪽을 권했어요. 에이전트는 채팅 화면, 에이전트 루프, 관리자 화면을 전부 직접 짰다고 스스로 짚었어요.

일하는 방식도 제가 바꿨어요. 다시 만들 때는 대형 워크플로를 켜지 않고, 태스크 단위로 잘라 메인 에이전트와 서브에이전트로 개발하는 게 시간 관계상 낫겠다고 했어요. 에이전트는 오히려 낫다고 했고, 지난 회차에는 화면을 보는 사람이 중간에 없었다고도 했어요. 그리고 조건 셋을 붙였어요. 태스크가 끝날 때마다 실제 화면 캡처와 실데이터로 확인하고, 태스크마다 작게 커밋하고, 두세 태스크마다 제가 화면을 확인하는 것이에요.

그날 저녁에 저는 이렇게도 말했어요.

> "그리고 만들 때 검증되고 업계에서 많이 쓰는 프레임워크 적극적으로 썼으면 하는 게 밑바닥부터 만드느라 시간, 토큰 소비가 많고 테스트도 오래 걸리고 UI도 삐뚤빼뚤 가고 그런 거 같아"

이 말은 결정 장부[^결정장부]에 '검증된 프레임워크와 라이브러리를 적극 쓰고, 직접 짜는 것은 우리 업무 규칙만'이라는 방침으로 올라갔어요. 처음 하는 말이 아니었어요. 그날이 세 번째였어요. 1차 버전을 만들 때도 저는 밑바닥부터 다 만드니 검수할 게 많고 의도치 않은 동작이 많다며, 바퀴를 다시 만들 필요는 없었다고 했어요. 기록에는 그때 에이전트가 '외부 의존 최소'를 제 방침으로 잘못 단정하고 있었다고 적혀 있어요. 두 번째로 말했을 때는 기존 것을 지나치게 부숴야 하면 들이지 않아도 된다는 말도 같이 했고, 그 조건이 장부 방침에 들어갔어요. 그날 에이전트는 바로 그 조건이 2차 구현 내내 교체를 막았다고 설명했어요.

지금 돌아봐도, 처음에 대형 워크플로로 화면과 도우미를 프레임워크 없이 밑바닥부터 길게 짠 탓에 테스트에서 결함이 많았던 것 같아요. 다만 이건 제 진단일 뿐 실제로 재 본 것은 아니에요. 그날 짚은 결함 셋 가운데 둘은 도우미의 LLM 답에서 났고, 화면 프레임워크와는 다른 자리의 문제였어요.

## 그날 다시 적은 '끝'에는 사람이 보는 자리가 들어갔고, 일정은 제가 추천과 다르게 골랐어요

그날 저녁 에이전트가 쓴 재기획서와 실행계획에 새로운 '끝'의 기준이 적혔어요. 태스크는 테스트 개수로 끝을 판정하지 않고, 아래 네 가지를 모두 채워야 끝이에요.

- 운영 데이터 사본을 띄운 PC 미리 보기에서 넓은 화면(1440px)과 좁은 화면(390px) 캡처
- 해당 테스트 통과
- 화면 · 대화 결함 목록에서 그 태스크 몫이 0
- 작은 커밋

여기에 사람의 확인 지점 넷(디자인 선택, 화면계획서 승인, 직접 써 보기, 전환 여부 판단)과 멈춤 기준을 더했어요. 직접 써 보기에서 high 결함이 남으면 전환(새 방식으로 넘어가는 일)을 한 달 미루고, 배포는 고친 만큼만 하되 기능 스위치는 끈 채 둔다는 것이에요. 이 기준은 에이전트가 제안했어요. 결정 장부에는 앞의 조건 셋에 제가 이의를 달지 않았고, 실행계획 초안은 제가 승인했다고 적혀 있어요. 전환을 미룬다는 규칙 자체는 그 전에 장부에 있던 것을 멈춤 기준으로 가져온 것이에요.

일정은 두 가지 안이 있었어요. 지금 버전을 고쳐 예정일에 전부 내는 안과, 예정일에는 미룰 수 없는 것만 열고 새로 정리한 버전은 한 달 뒤에 내는 안이에요. 에이전트는 뒤의 안을 추천했어요. 돈이 움직이는 기능은 제 원칙인 '확실성 먼저'대로 한 달 늦더라도 제대로 하자는 것이 이유 가운데 하나였어요. 앞선 안의 위험 항목에는 그날 10분 사용에 결함이 세 건 나와 남은 결함의 규모를 모른다는 줄이 적혀 있었어요. 저는 지금 것을 고쳐 예정대로 내자고 했어요. 그보다 20분쯤 전에 제가 쓴 기획 메모에는 예정일 전에 전부 완성해 사내에 배포하고 전 직원에게 공지한다고 적혀 있었어요. 예정일이 월초라, 날짜에 기대는 데이터가 깔끔하게 도는지 볼 수 있어서 그렇게 정했던 것으로 기억해요. 뒤의 안을 왜 받아들이지 않았는지 그날 따로 말한 기록은 없어요.

화면은 동작 코드를 그대로 두고 겉모양만 검증된 CSS 프레임워크로 바꾸자는 것이 에이전트의 추천이었어요. 새로 짜는 안은 남은 기간 안에 품질을 지킬 수 없다며 뒤로 미뤘어요. 프레임워크는 에이전트가 시안 셋을 견줘 Tabler를 추천했어요. 기존 요소에 클래스만 바꿔 입혀서, 동작 코드와 테스트가 요소를 찾는 선택자는 그대로 남는 방식이었어요. 제외한 두 후보 가운데 하나는 기본 설정이 보안 정책에 걸렸고, 다른 하나는 1년 동안 새 버전이 나오지 않았어요. 저는 두 가지 모두 권고대로 하자고 했어요.

## 첫 주에는 에이전트의 점검이 기준대로 돌았고, 사람이 보는 자리는 밀리거나 에이전트에게 넘어갔어요

새 기준의 첫 적용은 그날 저녁이었어요. 서브에이전트가 미리 보기의 직원 · 관리자 화면을 두 가지 화면 폭으로 전부 찍어 잘림 · 가림을 자동으로 점검하고, 실제 모델과 10턴을 대화했어요. 캡처 283장에서 결함 60건(high 12 · mid 25 · low 23)이 나왔고, high 가운데 6건은 화면 모양이 아니라 도우미의 답과 카드 쪽 문제였어요.

그날 밤 서브에이전트들이 재현 테스트를 먼저 쓰고 도우미를 고쳤어요. 데이터를 묻는 추천 질문은 LLM 없이 서버가 카드로 답하게 하고, 화면에 없는 카드나 버튼을 가리키는 문장은 빼고, 끊긴 답은 마지막 온전한 문장까지만 남겼어요. 수정 전후로 실제 모델에 같은 10턴을 돌려 보니 끊긴 답은 2에서 0, 없는 버튼 언급은 6에서 0, LLM이 답한 턴은 9에서 4가 됐어요. 다만 이 수정 사항을 커밋할 때 서버를 띄워 끝까지 도는 테스트는 돌리지 않았어요. 남아 있던 옛 기대값 하나가 며칠 뒤 배포 리허설에서 드러났어요.

끊긴 답에 대해 에이전트는 그날 저녁 짧은 질문으로 실측해 본 뒤 추론 토큰이 출력 상한을 나눠 쓴다는 가설을 세우고 추론 강도[^추론강도]를 low로 낮췄어요. 다음 날 새벽 실데이터 문맥으로 호출 86개를 재 보니 low에서도 추론 토큰이 최대 727(출력 상한 1,200의 61%)이어서 상한을 2,500으로 올렸어요. 이 수치는 우리가 쓴 모델과 설정에서 본 것이고, 34자로 끊긴 그 턴의 추론 토큰은 잰 적이 없어요. 설정을 바꾸기 전에 넘어야 하는 관문(합성 고정 질문 8문항을 실제 모델에 두 번씩)은 판정을 그대로 두고 문구를 고쳐 연속 두 번 16/16으로 넘겼어요([둘째 글](/posts/voice-bot-text-harness/)에서 판정과 통과 수를 다뤄요).

반면 사람이 보는 자리는 이렇게 돌아가지 않았어요. 그날 밤 에이전트는 실행계획의 사용자 화면 확인 지점이라며 캡처 몇 장과 테스트 기대값 변경 승인 한 건, 다음 묶음을 이어 가도 되는지를 한 메시지에 담아 보냈고, 저는 2분 뒤 '승인' 한마디로 답했어요. 저는 캡처를 보통 열어 보는 편이지만, 양이 많으면 요약만 보고 승인한 적도 있어요. 그날 밤이 어느 쪽이었는지는 기억나지 않아요. 다음 날 오전에 수정과 관문 통과가 끝났지만, 저는 직접 써 보기를 다음 세션으로 미뤘어요. 사내 공지가 급하다는 이유였어요.

직접 써 보기는 결함을 찾고 며칠 뒤에야 했어요. 에이전트가 운영 사본을 다시 띄웠고, 저는 로그인해 질문을 몇 개 해 본 뒤 이렇게 말했어요.

> "좀 살펴봐 봐. 답변 내용이나 스크롤도 내리면서 UI적으로도 어색한 거 없나 검토하고"

에이전트가 브라우저를 조작하는 도구로 모델 답 8건을 DB 원문과 대조했어요. 2건이 잘려 있었는데, 설치 때 운영 DB에 저장된 옛 설정값이 쓰이고 있었어요. 둘째 결함을 막으려고 넣은 처리가 조건을 설명하는 문장까지 지운 것도 드러났어요. 에이전트는 재현 테스트부터 써서 고쳤고, 브라우저 전 구간 테스트는 돌리지 않았다고 스스로 적었어요. high 결함은 그날 다 고쳐져 멈춤 기준은 발동하지 않았어요.

기록에 남은 것은 제가 질문을 몇 개 해 본 뒤 그 말을 했다는 것까지예요. 제 기억으로는 화면을 훑어봤는데, 어색한 곳을 말로 옮기기 애매했고 하나하나 캡처해 전하기에는 양이 많아서 에이전트에게 브라우저로 직접 보라고 했어요. 그날 결함을 원인까지 찾아 적은 것은 에이전트였어요. 그다음 날 기능 스위치를 끈 채로 이 버전을 운영에 배포했어요.

## 한 달 뒤, 화면을 프레임워크로 다시 짠 대시보드 버전을 배포하기 전에 기능을 끝까지 돌려 봤어요

마감 열흘쯤 뒤, 저는 결함 셋 가운데 둘이 나왔던 도우미를 걷어 내고 직원 · 관리자 화면을 대시보드로 개편하기로 했어요. 그때 저는 챗봇이 UI적으로 사소하게 틀리는 게 너무 많고, 쓰는 사람 대부분이 특정 기능만 쓸 것 같은데 굳이 예측이 안 되는 LLM 챗봇을 괜히 넣은 것 같다고 말했어요. 재활용할 수 있는 것은 최대한 재활용하겠다고도 했어요. 기록에는 그 전날 제가 직접 다 테스트해 보겠다고 한 말이 남아 있어요. 그때 말한 사소하게 틀리는 것들은 제가 직접 테스트하다 발견했던 것으로 기억해요. 고쳐 달라는 지시도 꽤 많이 했던 것으로 기억해요.

개편의 첫 작업들은 다시 옛 방식대로 진행됐고, 에이전트의 메모에는 작업을 시작할 때 의존 방침을 짚지 않았다고 남아 있어요. 11월 초 저는 같은 방침을 네 번째로 말하며 레퍼런스가 많다는 프레임워크 셋을 꺼냈어요. 에이전트는 Next.js를 쓰면 서버가 둘이 되고 인증이 겹치며, Django 관리자 화면을 쓰면 DB 행을 바로 고치게 되어 계획 · 미리 보기 · 감사 기록을 건너뛴다며 두 후보를 제외하고, React에 UI 키트를 더하는 안을 권했어요. 저는 그 안을 골랐어요. UI 키트는 그 뒤 에이전트가 관리자 메뉴 하나를 Mantine과 Ant Design으로 각각 시범 구현해 견줬고, 저는 비교표를 보고 추천대로 Ant Design을 골랐어요. 대시보드 형태로 다시 개발한 이 버전에서는 서버의 도우미와 끝난 기능을 걷어 내고 API를 보탰고, 업무 규칙은 프레임워크와 상관없는 파일로 따로 뺐어요.

배포 전날, 에이전트가 다시 운영 데이터 사본으로 미리 보기를 띄웠어요. 하루 전 가짜 데이터로 세 항목만 본 자동 점검은 깨끗했지만, 실데이터에서는 내부 식별자가 화면에 나오고 화면 간 숫자가 어긋났어요. 이 미리 보기에도 실행기가 없어, 한도를 나눠 주는 핵심 기능은 '접수'까지만 볼 수 있었어요. 에이전트는 이 한계를 먼저 알리지 않았고, 저는 90초 동안 도는 [지금 다시 확인]을 버그로 알고 되물었어요. 에이전트는 대기 상한을 30초로 줄였고, 미리 보기의 한계는 화면을 넘길 때 먼저 알린다는 규칙을 자기 메모에 적었어요.

다음 날 아침, 에이전트가 착수 계획을 내놓은 직후 저는 이렇게 말했어요.

> "다른 팀이 쓴 거 보니깐 한도 주고받는 건 기능 오류 없이 잘되는 거 같던데 디자인 실컷 바꿨더니 기능 안 되는 일이 있으면 안 돼. 알지? 당연히"

에이전트가 바로 재 보니 서버 코드도 이백 파일쯤 바뀌어 있었어요. 대부분은 도우미와 끝난 기능을 지운 줄이었어요. 새 화면에서 누른 나눠 주기가 진짜 실행기를 거쳐 반영까지 이어지는지 본 테스트는 없었고, 이대로면 배포 뒤 운영에서 처음 맞닥뜨리게 된다고 에이전트가 먼저 짚었어요.

에이전트가 짠 확인 단계는 핵심 기능을 화면부터 끝까지 돌려 보는 테스트였어요(추천안은 여덟 개였고, 배포 전에는 열 개가 됐어요). 화면에서 누르면 진짜 포털과 진짜 실행기를 거쳐 가짜 외부 서비스에 쓰고, 그 결과가 새로 고침 없이 화면에 돌아오는지를 봐요. 범위와 순서는 에이전트가 제안했고, 저는 추천안을 골랐어요.

이 테스트에서 날짜를 다루는 관리자 기능 하나에서 저장된 시각이 조금 앞당겨지는 결함이 드러났는데, 옛 화면에서 물려받은 것이었어요. 두 화면의 코드를 대조한 조사는 새 화면이 같은 기능에서 날짜만 보내 서버가 시간대를 어긋나게 읽는 것과, 빠진 옛 동작 몇 가지를 찾았어요. 그 시간대 회귀 버그는 새 화면으로 테스트를 옮기며 제가 한꺼번에 승인했던 기대값 변경 가운데 하나에 섞여 있었어요. 모두 배포 전에 고쳤어요.

배포 직전 저는 되돌릴 수 있게 백업하고 배포하는 거냐고 물었어요. 에이전트는 DB 백업은 자동으로 뜨지만, DB 구조가 바뀌는 배포라 되돌리기는 손으로 해야 한다고 답했어요. 배포 스크립트는 제가 돌렸어요. 배포 직후 저는 관리자 화면에 들어가 승인을 기다리던 신청 하나를 승인했고, 8초 만에 반영됐어요. 직원 화면의 [지금 다시 확인]도 제가 눌러 봤고, 실행기가 2초 만에 처리했어요. 에이전트가 제안했던, 실제 계정으로 나눠 주기를 한 번 돌려 보는 단계는 넣지 않았어요. 나눠 주기는 개편 전에 테스트했고, 배포돼 있던 버전을 다른 팀이 쓰는 모습을 보며 정상 동작도 확인했어요. 그 부분을 건드리지 않았다면 똑같이 동작할 거라고 봤기 때문이에요. 이 확인 단계에서도 외부 서비스는 끝까지 가짜였고, 배포 뒤 다듬을 것이 남아 있어요.

## 다시 적은 '끝'은 지켜진 곳도 있고 어긴 곳도 있어요

이 글을 준비하며 결함을 찾은 날부터의 기록을 날짜순으로 늘어놓았어요.

| 언제 | 결과 | 무엇 |
|---|---|---|
| 그날 저녁 · 밤 | 지켜짐 | 캡처 283장과 실제 모델 10턴 → 결함 60건 · 수정은 재현 테스트 먼저 |
| 그날 밤 | 어긋남 | 같은 수정 때 끝까지 도는 테스트를 건너뜀 → 며칠 뒤 드러남 |
| 그날 밤 | 기록만 | 사용자 화면 확인 지점에 2분 뒤 승인 |
| 다음 날 오전 | 어긋남 | 직접 써 보기를 공지 일정 때문에 미룸 |
| 며칠 뒤 | 반쯤 | 직접 써 보기는 제가 조금, 점검은 에이전트가 · 브라우저 전 구간 테스트는 안 돌림 |
| 그다음 날 | 지켜짐 | 배포 뒤 직원 화면 확인 · 설정 적용 전 관문 16/16 |
| 11월 초 | 어긋남 | 개편 첫 작업이 옛 방식대로 진행됨 · 의존 방침을 네 번째로 말함 |
| 배포 이틀 전 | 반쯤 | 새 화면 자동 점검은 가짜 데이터 · 일괄 승인한 기대값 변경에 회귀 버그가 섞임 |
| 배포 전날 | 지켜짐 · 빈틈 | 운영 사본 미리 보기 / 실행기가 없어 핵심 기능은 '접수'까지만 |
| 배포 날 | 지켜짐 | 제 한마디로 화면 → 포털 → 실행기 끝까지 · 배포 직후 실제 쓰기 1건 |

기준대로 돌아간 것은 대부분 에이전트가 자기 손으로 하는 점검(캡처 · 재현 테스트 · 실제 모델 대화)이었어요. 사람이 보는 자리는 2분 만의 승인으로 지나가거나, 공지 일정에 밀리거나, 자세한 점검이 에이전트에게 넘어갔어요. 한 달 뒤의 확인 단계는 기준 문서가 아니라 제 한마디로 시작됐어요. 제가 보기에는 적어 둔 기준보다 사람이 직접 말한 순간에 그 확인이 더 잘 일어났어요.

## 확인하지 못한 것

한 달 뒤의 확인 단계에서도 외부 서비스는 가짜였어요. 실제 계정으로 돌려 본 것은 배포 직후의 승인 한 건과 다시 확인뿐이에요. 배포 뒤 직원들이 실제로 쓴 결과는 아직 확인하지 못했어요. 이 글을 쓰는 지금은 배포한 지 얼마 되지 않았어요. 출시 뒤 사용 지표도 기록에 없어요.

화면과 도우미를 프레임워크 없이 짠 것과 결함 수의 관계는 잰 적이 없어요. 두세 태스크마다 하기로 한 사용자 화면 확인이 첫날 밤 뒤로 몇 번 더 돌았는지도 찾지 못했어요.

기억으로도 채우지 못한 것이 있어요. 마감 보고의 "구현을 끝냈습니다"를 그때 제가 어떤 뜻으로 받아들였는지는 기록에 없고, 지금은 저도 기억나지 않아요. 본문에서 "기억해요"라고 적은 이유들은 그날의 기록이 아니라 이 글을 쓰며 떠올린 것이에요.

## 다시, "구현을 끝냈습니다"로

맨 앞의 보고는 거짓이 아니었어요. 테스트는 정말 모두 통과했어요. 다만 그 테스트는 가짜 외부 서비스와 녹화된 응답 위에서 돌았어요. 그날 '끝'의 기준에 사람이 보는 자리를 적어 넣었지만, 적어 둔 것만으로 그 자리가 채워지지는 않았어요. 무엇 위에 지을지도 그랬어요. 방침은 장부에 적힌 뒤에도 다시 말해야 했어요. 화면을 프레임워크와 UI 키트로 다시 짠 버전이 나간 것은 한 달 뒤예요.

다시 한다면 바꿀 점들이에요. 첫째 · 둘째 · 넷째는 에이전트가 그때 자기 메모에 규칙으로 적어 둔 것이고, 셋째는 이 글을 정리하며 기록에서 뽑았어요.

- '끝'을 보고하기 전에, 사람이 쓰는 줄기 하나(화면 → 서버 → 실행기 → 결과 화면)를 한 번은 끝까지 돌려요.
- 새 작업을 시작할 때 무엇 위에 지을지, 즉 의존 방침부터 짚어요. 개편 첫 작업에서는 이를 짚지 않았어요.
- 테스트 기대값 변경을 한꺼번에 승인하기 전에, 화면이 서버에 보내는 값이 바뀌는 건은 따로 대조해요.
- 미리 보기에 무엇이 빠져 있는지(실행기 같은 것)를 사람이 보기 전에 먼저 알려요.

'끝'이라는 말의 근거는 테스트였고, 그 말이 무엇을 빠뜨렸는지는 다음 날 사람이 10분 남짓 써 보고서야 드러났어요.

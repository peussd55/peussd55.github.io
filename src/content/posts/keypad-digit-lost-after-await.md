> - **문제** — 전화 음성 봇에서 키패드를 빨리 누르면 숫자 한 자리가 가끔 빠진 채 들어왔어요. 같은 입력인데 될 때도 있고 안 될 때도 있었어요.
> - **원인** — 통화 상태를 맵에서 꺼내 고치고, `await`를 지난 뒤에 그 복사본을 맵에 되쓰는 코드였어요. 기다리는 사이에 다른 핸들러가 쓴 값이 덮였어요. 같은 한 줄이 한 파일에 28곳 있었고 그 가운데 한 곳만 터졌어요.
> - **한 일** — 6월에 그 한 곳을 고쳤는데, 3주쯤 뒤 다른 자리에서 같은 증상이 났어요. 그때는 상태를 쓰는 39곳을 전부 분류해 위험한 곳을 한꺼번에 고쳤어요.
> - **확인한 것과 못 한 것** — 고친 뒤 직접 전화를 걸어 세 가지 입력 상황을 확인했고, 그 뒤로 같은 증상으로 들어온 요청은 없었어요. 고치기 전과 후에 얼마나 자주 빠졌는지 센 기록은 없어요.

## 숫자가 지나가는 길

전화를 받아 말로 응대하는 음성 봇 이야기예요. 번호 같은 값은 키패드로 받아요. 상대가 숫자를 누르고 `#`으로 끝내요.

키패드 입력(DTMF)은 한 번에 오지 않아요. 키를 누를 때마다 전화 교환기(PBX)가 이벤트를 하나씩 보내요. 봇 서버는 그 한 글자를 통화 상태의 버퍼에 붙이고, 교환기 쪽에도 HTTP로 값을 적어 둬요. `#`이 오면 버퍼에 쌓인 숫자를 모델에게 넘겨요.

통화 상태는 채널 ID를 키로 하는 맵 하나에 들어 있어요. 버퍼뿐 아니라 지금 재생 중인 음성이나 대기음을 틀었는지 같은 값이 한 객체에 같이 있어요. 서버는 Node.js예요.

## 빨리 누르면 가끔 한 자리가 빠졌어요

숫자를 빠르게 이어 누르면 가끔 한 자리가 빠진 채 봇에 들어왔어요. 빠르게 눌러도 대부분은 괜찮았고, 일부러 다시 재현해 보려 해도 잘 나오지 않았어요. 제 기억으로는 전부터 제가 알고 있던 증상이고, 풀리지 않은 채 남아 있었어요. 6월에 코딩 에이전트에게 이 증상을 알려 줬어요.

## 원인은 await 뒤에 되쓴 복사본이었어요

에이전트가 짚은 원인은 숫자 핸들러에 있었어요. 뼈대만 남기면 아래와 같아요.

이 글의 코드는 실제 업무 코드가 아니에요. 문제를 재현하려고 같은 모양으로 새로 쓴 코드이고, Node.js에서 그대로 돌아가요.

```js
const sleep = (ms) =>
  new Promise((r) => setTimeout(r, ms));
// 채널 ID → 통화 상태
const calls = new Map();

// 교환기에 값을 쓰는 HTTP 호출을 흉내 내요.
// 응답이 돌아오는 순서는 매번 달라요.
const writeToPbx = () =>
  sleep(10 + Math.random() * 50);

async function onDigit(id, digit) {
  const call = calls.get(id);
  call.digits += digit;
  await writeToPbx();
  await writeToPbx();
  // 복사해서 다시 set
  calls.set(id, { ...call });
}

calls.set('ch1', { digits: '' });
const pending = [];
for (const key of '12345678') {
  pending.push(onDigit('ch1', key));
  await sleep(60); // 0.06초마다 눌러요
}
await Promise.all(pending);
// 12345678이 나와야 해요
console.log(calls.get('ch1').digits);
```

제 PC에서 100번 돌리니 여덟 자리가 다 나온 것은 15번이었어요. 85번은 `12468`, `123468`처럼 중간 숫자가 빠졌어요. 이 비율은 실제 빈도가 아니에요. 증상이 잘 나오도록 키 간격을 좁게 잡아서 나온 결과예요. 실제 통화에서는 가끔이었어요.

빠지는 순서는 이래요.

1. 키 1의 핸들러가 맵에서 객체 X를 꺼내 `1`을 붙이고, 교환기의 응답을 기다려요.
2. 키 2의 핸들러가 같은 X에 붙여요. X는 `12`가 돼요.
3. 키 1의 핸들러가 깨어나 X의 복사본 Y를 맵에 넣어요. 맵에는 이제 Y(`12`)가 있어요. 여기까지는 문제가 없어요.
4. 키 3의 핸들러는 맵에서 Y를 꺼내 붙여요. Y는 `123`이 돼요.
5. 키 2의 핸들러가 깨어나, 들고 있던 X(`12`)의 복사본을 맵에 넣어요. Y에 붙인 `3`은 맵에서 사라져요.
6. 이 틈에 키 4가 들어오면 `124`가 돼요. 그 뒤 키 3의 핸들러가 깨어나 `123`으로 다시 덮으면, 이번에는 `4`가 사라져요.

마지막에 쓴 쪽이 이겨요. 어느 핸들러가 먼저 깨어나는지는 HTTP 응답이 돌아오는 순서에 달려 있어서, 같은 입력도 될 때가 있고 안 될 때가 있었어요. 빨리 누를수록 기다리는 구간이 서로 겹치니 더 자주 생겨요.

`Map.get`이 돌려주는 것은 복사본이 아니라 살아 있는 참조예요. 꺼낸 객체를 고치면 맵 안의 값은 이미 바뀌어 있어요. 이 핸들러는 복사해서 다시 넣지 않아도 값이 남는데, 그 복사가 객체를 둘로 갈라 놓았어요. 같은 일을 하는 다른 방식의 핸들러는 꺼낸 객체를 제자리에서 고치기만 했는데, 거기서는 이 증상이 없었어요.

이 한 줄은 그 파일에 28곳 있었어요. 그때 본 바로는 27곳이 멀쩡했어요. 꺼내고 넣는 사이에 `await`가 없거나, 동시에 들어오는 입력이 없는 자리였어요. 숫자 핸들러 한 곳에서만 두 조건이 겹쳤어요. 똑같이 생긴 코드 28곳 가운데 하나만 터지니, 읽어서는 잘 보이지 않았어요.

## 6월에는 저장하는 순서만 옮겼어요

수정은 작았어요. 맵에 넣는 줄을 `await` 앞으로 옮기고, 뒤에서 되쓰던 줄을 뺐어요. 다른 로직은 건드리지 않았어요.

```js
async function onDigit(id, digit) {
  const call = calls.get(id);
  call.digits += digit;
  // await 앞에서 넣어요
  calls.set(id, { ...call });
  await writeToPbx();
  await writeToPbx();
  // await 뒤에는 되쓰지 않아요
}
```

재현 코드의 핸들러를 이렇게 바꾸면 100번 모두 여덟 자리가 나와요.

고친 뒤 실제 봇에서도 빠르게 눌러 다시 확인했어요. 제 기억으로는 그 뒤로 빨리 누를 때 한 자리가 빠지는 일은 다시 없었어요. 이 확인은 기록에는 남아 있지 않아요.

이 수정은 앱 안의 원인만 없애요. 키패드 신호가 전화망에서 빠지는 경우는 따로예요. 그래서 고친 뒤에도 증상이 남으면 가를 방법을 같이 적어 두었어요. 교환기가 받은 키 이벤트의 수와 우리 버퍼의 길이를 비교하면, 망에서 빠졌는지 앱에서 빠졌는지가 갈려요.

그리고 한 곳을 일부러 남겼어요. `#`을 받아 입력을 마무리하는 쪽에도 같은 모양이 있었어요. `#`은 한 번만 누르는 키라 겹칠 일이 사실상 없다고 보고, 바꾸는 범위를 줄였어요. 이 판단이 틀렸어요.

## 3주 뒤, 봇이 말하는 도중에 누른 숫자가 사라졌어요

7월 초에 봇의 말을 재생하는 방식을 바꿨어요. 전에는 새 문장이 오면 재생 중이던 문장을 밀어냈어요. 그래서 모델이 "잠시만요" 같은 말과 실제 답을 연달아 내보내면 앞 문장이 잘렸어요. 순서대로 끝까지 재생하는 큐로 바꿨어요.

며칠 뒤 숫자가 다시 사라졌어요. 이번에는 세 가지였어요.

- 봇이 말하는 도중에 누르면 앞자리가 사라져요. 가장 잘 재현됐어요.
- 봇의 말이 끝난 뒤에 눌러도 가끔 사라져요. "잠시만요"와 실제 답 사이의 조용한 틈에 누른 경우가 대부분이었을 것으로 봐요(추정이에요).
- `#`을 누른 직후 다음 항목을 바로 누르면 앞자리가 사라져요.

원인은 같은 병이었어요. 재생이 끝나면 재생 상태를 정리하는 코드가 있어요. 이 코드는 음성합성(TTS)을 시작하기 전에 잡아 둔 객체를 고쳐서, 그 복사본을 맵에 되쓰고 있었어요. 그 사이 맵의 객체는 여러 번 새 복사본으로 바뀌는데, 이 코드는 처음에 잡은 객체를 계속 들고 있었어요.

```js
async function speak(id, ms) {
  // 재생을 시작할 때 잡은 객체
  const call = calls.get(id);
  calls.set(id, {
    ...call,
    speaking: true,
  });
  await sleep(ms); // 재생이 끝날 때까지
  calls.set(id, {
    ...call, // 처음에 잡은 객체를 되써요
    speaking: false,
  });
}
```

앞의 재현 코드에 이 함수를 더해 봤어요. 핸들러는 6월 수정본으로 두고, 봇이 0.25초 말하는 동안 키를 0.1초 간격으로 누르게 했어요(`pending`을 `[speak('ch1', 250)]`으로 시작하고 `sleep(60)`을 `sleep(100)`으로 바꿔요). 100번 모두 `45678`이 나왔어요. 말하는 도중에 누른 세 자리가 사라진 거예요.

이 되쓰기는 6월 전부터 있던 코드예요. 그때의 기록에는 재생 큐가 이런 틈을 새로 만들거나 넓혔다고 적혀 있어요. 재생이 끝날 때 맵을 덮는 객체는 합성을 시작하기 전에 잡은 것이라 수 초 묵은 것이었어요.

세 번째 증상은 6월에 남겨 둔 그 자리였어요. `#`을 처리하며 기다리는 수백 밀리초 사이에 다음 항목의 첫 숫자가 들어오면, 뒤에서 되쓰는 줄이 그 숫자를 지웠어요. `#`은 한 번만 누르지만, 그 뒤에 곧바로 다음 입력이 이어진다는 것을 놓쳤어요.

## 이번에는 쓰는 자리를 전부 분류했어요

증상이 난 곳만 다시 고치면 6월과 같은 일이 반복돼요. 그래서 이 파일에서 통화 상태를 맵에 넣는 39곳을 전부 열어, 꺼내는 시점과 넣는 시점 사이에 시간이 끼는지를 기준으로 나눴어요. `await`, 이벤트, 타이머가 끼는 자리가 위험한 자리예요.

숫자를 지우는 자리는 다섯 곳이었어요. 다섯 곳 모두 로직은 그대로 두고, 저장하는 대상이나 시점만 바꿨어요. 대부분은 들고 있던 객체 대신 쓰는 시점에 맵에서 다시 꺼낸 객체를 쓰게 했어요. `#` 쪽은 6월처럼 `await` 앞에서 넣게 했어요.

```js
  calls.set(id, {
    ...calls.get(id), // 지금 다시 꺼내요
    speaking: false,
  });
```

재현 코드에서 `speak`의 마지막 `calls.set`을 이렇게 바꾸면 100번 모두 여덟 자리가 남아요.

## 고치자 가려져 있던 버그가 나왔어요

수정을 올린 날, 사내 운영 봇에서 대기음이 나오지 않았어요. 봇이 도구를 실행하는 동안 틀어 주는 대기음(MOH)이에요. 첫 번째 도구 호출에서는 나왔는데 두 번째부터는 조용했어요. 말로만 응대하는 다른 봇은 괜찮았어요.

대기음 코드는 "지금 켜져 있나"를 통화 상태 객체에 적어 두고, 같은 상태로 바꾸라는 요청은 건너뛰어요. 그런데 "껐다"를 적는 대상이 넘겨받은 묵은 객체였어요. 맵의 최신 객체에는 "켜짐"이 그대로 남았고, 다음 도구 호출에서 켜려 하면 이미 켜져 있다고 보고 건너뛰었어요.

전에는 이 결함이 드러나지 않았어요. 재생이 끝날 때의 묵은 되쓰기가 "껐다"를 맵으로 옮겨 주고 있었기 때문이에요. 버그 하나가 다른 버그를 가리고 있었고, 앞의 것을 고치자 뒤의 것이 나왔어요.

이 봇에서만 문제가 난 이유도 같은 줄기예요. 키 입력이 많은 봇이었어요. 6월 수정은 숫자가 들어올 때마다 맵의 객체를 새 복사본으로 바꿔요. 그만큼 묵은 객체와 최신 객체가 갈라지는 일이 잦았어요. 6월의 수정도 복사해서 넣는 방식은 그대로 둔 채 순서만 옮긴 것이었어요.

대기음 쪽도 넘겨받은 객체가 아니라 맵에서 다시 꺼낸 객체를 기준으로 판단하게 고쳤어요. 이것까지 여섯 곳을 같은 날 고쳤고, 나머지 33곳은 꺼내고 넣는 사이에 시간이 끼지 않아 그대로 뒀어요.

## 확인한 것과 남은 것

증상을 알린 것은 저이고, 원인은 코딩 에이전트가 코드에서 짚었어요. 39곳의 분류와 수정도 에이전트가 했어요. 7월에는 개발 서버에 올린 뒤 제가 직접 전화를 걸어 눌러 봤어요. 봇이 말하는 도중에 연달아 누르기, 말과 말 사이에 누르기, `#` 직후에 다음 항목 누르기예요. 세 경우 모두 누른 숫자가 다 들어왔어요. 사내 운영 봇에 도구 호출을 이어서 시켜 대기음이 나오는 것, 순서대로 재생하는 큐가 그대로 도는 것도 같이 봤어요. 그 뒤로 같은 증상으로 들어온 요청은 없었어요.

확인하지 못한 것은 이래요.

- 얼마나 자주 빠졌는지 센 기록은 고치기 전에도 후에도 없어요. 확인은 제가 손으로 해 본 상황들이 전부예요.
- 전화망 쪽을 가르는 대조를 해 봤다는 기록은 찾지 못했어요. 6월 수정 뒤에 다시 눌러 본 것도 기록이 아니라 제 기억이에요.
- 재생 큐를 넣기 전에는 왜 같은 증상이 드러나지 않았는지는 코드로 끝까지 따라가지 않았어요.
- 무해하다고 본 33곳은 그대로예요. 지금은 꺼내고 넣는 사이에 시간이 끼지 않아서 무해한 거예요. 누가 그 사이에 `await` 한 줄을 넣으면 같은 버그가 돼요.

다시 한다면 바꿀 것은 두 가지예요.

- **남기는 판단을 줄여요.** 6월에 "여기는 겹칠 일이 없다"고 남겨 둔 한 곳이 3주 뒤의 재발 지점이 됐어요. 같은 모양이 여러 곳이면, 증상이 난 곳만 고치지 않고 처음부터 전부 분류해요.
- **타이밍을 바꾸는 변경 뒤에는 상태를 쓰는 자리를 다시 봐요.** 재생 큐는 숫자 입력과 상관없는 변경이었지만, 그 뒤에 같은 병이 다른 자리에서 났어요.

새로 쓰는 코드에는 규칙 하나를 뒀어요. `await` 뒤에서는 들고 있던 객체의 복사본을 맵에 넣지 않아요.

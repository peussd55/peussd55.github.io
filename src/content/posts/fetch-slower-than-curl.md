> - **문제** — 고객사 콜봇이 질문마다 부르는 지식 검색 호출이 제한 시간 5초를 넘겼어요. 구간별로 재 보니 첫 요청의 인덱스 로드가 2초를 넘었고, 닷새 뒤 기록에는 질문을 벡터로 바꾸는 임베딩 API 호출이 1,049ms로 적혀 있어요. 같은 호출을 curl로 잰 값은 333ms였어요.
> - **원인** — 우리 코드는 Node.js 내장 `fetch`로 임베딩 API를 부르고 있었는데, 맺은 연결을 다음 호출에서 다시 쓰지 못하고 있었어요.
> - **한 일** — 임베딩 호출을 keep-alive를 켠 HTTP 클라이언트로 바꾸고, 인덱스는 서버를 띄울 때 미리 읽게 했어요.
> - **확인한 것과 못 한 것** — 개발 서버에서 잰 임베딩 호출은 1,049ms에서 114\~149ms가 됐어요(몇 번 잰 값인지는 기록에 없어요). 그때 기록에는 원인이 "내장 fetch는 요청마다 새로 연결한다"고 적혀 있었는데, 이 글을 쓰며 문서와 재현 코드로 다시 보니 내장 `fetch`도 연결을 다시 쓰지만 4초 넘게 쉬면 닫는 거였어요. 똑같이 새 연결을 맺는 curl보다 0.7초 더 걸린 이유는 확인하지 못했어요.

## 제한 시간을 넘긴 검색 호출

고객사의 전화 상담 봇(콜봇) 이야기예요. 고객이 질문하면 봇은 지식 검색 모듈을 불러요. 검색 모듈은 외부 임베딩 API를 불러 질문을 벡터로 바꾸고, 메모리에 올려 둔 인덱스의 벡터들과 유사도를 계산해 가까운 답을 골라요.

3월 중순에 이 검색 호출이 제한 시간 5초를 넘겼어요. 어디서 시간이 걸리는지 볼 로그가 없었어요. 제한을 15초로 늘려 급한 불을 끄고, 검색 모듈에 구간별 타이밍 로그를 넣었어요. 인덱스 로드, 임베딩, 유사도 계산 세 구간이에요.

로그를 넣고 잰 값은 이랬어요. 서버를 띄운 뒤 첫 요청은 인덱스 파일을 읽는 데 2,435ms, 임베딩에 약 443ms가 걸렸어요. 그 뒤 요청은 임베딩 약 443ms에 유사도 계산 약 30ms였어요. 첫 요청이 올 때 인덱스를 읽고 있었던 거예요.

그날 기록에는 원인이 첫 요청의 인덱스 로드와 임베딩의 합으로 적혀 있고, 그 뒤 요청의 약 473ms 옆에는 "정상"이라고 적혀 있어요. 그런데 둘을 합쳐도 2.9초라 5초에는 못 미쳐요. 제한을 넘긴 그 요청은 로그를 넣기 전이라, 어느 구간이 얼마나 걸렸는지 남아 있지 않아요.

## 닷새 뒤 기록에 있던 curl 값

닷새 뒤 기록은 임베딩 호출을 고친 내용이에요. 여기에는 고치기 전 임베딩 호출이 1,049ms로 적혀 있어요. 같은 코드인데 첫날의 443ms와 왜 다른지, 닷새 사이에 무엇을 보고 임베딩을 다시 살펴봤는지는 기록에 없어요.

그 기록에는 같은 호출을 curl로 잰 값이 나란히 적혀 있어요. 333ms였고, 그중 TLS 핸드셰이크가 20ms였어요. curl은 호출할 때마다 연결을 새로 맺어요. 그 curl이 0.3초인데 우리 코드를 거친 호출은 1초였어요.

검색 모듈은 Node.js 내장 `fetch`로 임베딩 API를 부르고 있었어요.

## 고친 것

이 글의 코드는 실제 업무 코드가 아니에요. 문제를 재현하려고 같은 모양으로 새로 쓴 코드이고, 아래 첫 칸은 바꾼 모양만 보여 줘요.

```js
// 전: 내장 fetch로 바로 불러요
await fetch(EMBED_URL, {
  method: 'POST', headers, body,
});

// 후: keep-alive를 켠 Agent를 붙여요
const client = axios.create({
  httpsAgent: new https.Agent({
    keepAlive: true,
  }),
});
await client.post(
  EMBED_URL, payload, { headers },
);
```

바꾼 것은 셋이에요.

- 임베딩 호출을 keep-alive를 켠 `Agent`가 붙은 클라이언트로 바꿨어요. 한 번 맺은 연결을 다음 호출에서 다시 써요.
- 인덱스는 서버를 띄울 때 미리 읽게 했어요. 첫 요청이 2초 넘게 걸리는 인덱스 로드를 떠안지 않아요.
- 임베딩 호출 자체에도 타이밍 로그를 넣었어요.

개발 서버에서 잰 전후 값이에요. 그날 기록에 적혀 있고, 몇 번 잰 것인지는 기록에 없어요.

| 구간 | 전 | 후 |
|---|---|---|
| 임베딩 호출 | 1,049ms | 114\~149ms |
| 인덱스 로드(첫 요청) | 2,700ms | 0ms(기동 때 읽음) |
| 유사도 계산 | 26\~33ms | 그대로 |
| 검색 합계 | 첫 요청 3,775ms · 그 뒤 1,075ms | 약 158ms |

서버를 다시 띄운 직후 첫 임베딩 호출만 1초쯤 걸렸고, 그 뒤로는 통화를 끊고 다시 걸어도 130ms쯤으로 유지됐어요. 2,086ms가 한 번 찍힌 적이 있는데, 기록에는 상대 서버의 지연으로 적혀 있어요.

전화로 질문해서 답이 나오기까지 걸린 시간은 3,801ms에서 약 2,892ms로 줄었어요. 검색에서 줄어든 0.9초만큼이에요. 남은 2.9초 중 검색이 차지하는 시간은 0.2초가 안 돼요. 통화 전체를 구간별로 나눠 잰 내용은 [음성 상담봇의 응답 지연을 네 구간으로 나눠 본 글](/posts/who-knows-when-speech-ends/)에 있어요.

## 그때 적은 원인을 다시 확인했어요

수정 기록에는 원인이 이렇게 적혀 있어요. Node.js 내장 `fetch`는 요청마다 TCP와 TLS 연결을 새로 맺어서 1초쯤 걸리고, keep-alive를 켜면 한 번 맺은 연결을 다시 쓴다는 설명이에요. 그런데 연결을 새로 맺는 curl은 0.3초였어요. 이 글을 쓰면서 이 문장을 그대로 옮겨도 되는지 다시 확인했어요.

문서부터 봤어요. 내장 `fetch`는 Node.js에 들어 있는 HTTP 클라이언트 undici로 돌아가요. undici 문서에는 요청이 없는 연결을 닫는 시간(`keepAliveTimeout`)의 기본값이 4초이고, 서버가 keep-alive 힌트를 주면 그 값을 따른다고 적혀 있어요. 내장 `fetch`도 연결을 다시 써요. 쉬는 시간이 4초를 넘으면 닫을 뿐이에요.

다음은 재현이에요. 새 연결 수를 세는 서버를 띄우고, 요청 다섯 번을 1초 간격과 6초 간격으로 보내요. 아래 세 칸을 한 파일에 이어 붙이면 Node.js 24에서 그대로 돌아가요.

```js
import net from 'node:net';
// 새 연결 수를 세는 서버예요. 힌트를
// 주지 않고, 먼저 끊지도 않아요.
const OK = 'HTTP/1.1 200 OK\r\n' +
  'Content-Length: 2\r\n\r\nok';
const END = '\r\n\r\n';

function onSocket(s, sock) {
  s.connections += 1;
  let buf = '';
  sock.on('error', () => {});
  sock.on('data', (chunk) => {
    buf += chunk;
    if (!buf.endsWith(END)) return;
    buf = '';
    sock.write(OK);
  });
}

async function startServer() {
  const s = { connections: 0 };
  const server = net.createServer(
    (sock) => onSocket(s, sock),
  );
  await new Promise((r) =>
    server.listen(0, '127.0.0.1', r));
  const { port } = server.address();
  s.url = `http://127.0.0.1:${port}/`;
  return s;
}
```

```js
import http from 'node:http';

const sleep = (ms) => new Promise(
  (r) => setTimeout(r, ms),
);

// (가) 내장 fetch
async function viaFetch(url) {
  const res = await fetch(url);
  await res.text();
}

// (나) keep-alive 에이전트
const agent = new http.Agent({
  keepAlive: true,
});
function viaAgent(url) {
  return new Promise((resolve) => {
    const done = (res) => {
      res.resume();
      res.on('end', resolve);
    };
    http.get(url, { agent }, done);
  });
}
```

```js
// 요청 다섯 번을 gap 간격으로 보내고
// 서버가 센 새 연결 수를 돌려줘요.
async function run(call, gap) {
  const s = await startServer();
  for (let i = 0; i < 5; i += 1) {
    if (i) await sleep(gap);
    await call(s.url);
  }
  return s.connections;
}

const out = await Promise.all([
  run(viaFetch, 1000),
  run(viaFetch, 6000),
  run(viaAgent, 1000),
  run(viaAgent, 6000),
]);
console.log(out.join(' '));
process.exit(0);
```

```text
1 5 1 1
```

내장 `fetch`는 1초 간격이면 연결 하나로 다섯 번을 보내고, 6초 간격이면 다섯 번 모두 새로 맺어요. keep-alive를 켠 `Agent`는 두 간격 모두 하나예요. 100번 돌려서 100번 모두 같은 값이 나왔어요. 이 서버는 keep-alive 힌트를 주지 않아요. 문서대로라면 힌트를 주는 서버에서는 결과가 달라질 수 있어요.

전화 상담에서 검색 호출은 고객이 질문할 때마다 한 번씩 일어나요. 호출과 호출 사이에는 봇이 답을 읽고 고객이 다시 말하는 시간이 들어가요. 서버가 힌트를 주지 않는다면, 그 사이가 4초를 넘을 때 내장 `fetch`가 연결을 닫고 다음 호출에서 연결을 새로 맺어요. 고치기 전 임베딩 값(1,049ms)이 고친 뒤 재기동 직후 첫 호출 값(1초쯤)과 비슷했던 것도 이 설명과 맞아요.

사실과 달랐던 부분은 수정 기록의 원인 문장이에요. 내장 `fetch`는 연결을 다시 쓰지 않는 게 아니라, 쉬는 연결을 일찍 닫는 거예요. 고친 방향은 같아도 이유는 달랐어요. 재현대로라면 요청이 1초 간격으로 오는 서비스에서는 같은 코드로도 연결을 다시 써요.

## 확인한 것과 남은 것

3월 수정 기록에는 누가 무엇을 제안했는지 적혀 있지 않아요. 그래서 그때 일은 주어 없이 적었어요. 이번 재확인은 코딩 에이전트가 문서를 읽고 재현 코드를 써서 돌렸고, 저는 그 결과를 보고 원인 설명을 고쳐 쓰기로 했어요.

운영 서버의 소스를 7월에 떠 둔 사본에는 이 수정이 들어 있어요.

확인하지 못한 것은 이래요.

- 3월 그 서버에서 연결 수를 센 적은 없어요. 그 서버의 Node.js 버전도, 임베딩 API가 keep-alive 힌트를 주는지도 기록에 없어요. 재현은 지금의 Node.js에서 한 것이에요.
- 연결을 새로 맺는 curl이 333ms였는데 고치기 전 호출은 1,049ms였어요. 연결을 새로 맺는 비용만으로는 이 0.7초가 설명되지 않아요.
- 전후 값을 몇 번 쟀는지, 제한을 넘긴 요청이 어느 구간에서 걸렸는지, 한 번 찍힌 2,086ms가 무엇이었는지는 기록에 없어요.
- 운영 서버에서 잰 전후 값은 없어요.

다시 한다면 바꿀 점은 두 가지예요.

- **외부 호출의 시간을 잴 때는 다른 클라이언트로 잰 값을 옆에 둬요.** 기록에 남은 curl 값 하나가 원인 문장을 다시 보게 한 단서였어요.
- **원인에 "기본 동작이 그렇다"고 적기 전에 문서와 재현으로 확인해요.** 기본값의 숫자(4초)와 우리 호출 간격을 같이 봐요.

이 글의 일은 코딩 에이전트와 함께 했어요. 무엇을 누가 했는지는 본문에 적었어요.
